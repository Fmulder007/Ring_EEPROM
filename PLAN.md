# Ring_EEPROM — план проектирования универсальной библиотеки кольцевой записи

> **Статус документа:** проект обсуждения.  
> **Назначение:** собрать в одном месте согласованные идеи, предварительные решения, технические ограничения и открытые вопросы до начала реализации.  
> **Язык документации проекта:** русский.  
> **Важно:** это не окончательная спецификация алгоритма. Предварительные решения требуют обсуждения и утверждения.

---

## 1. Цель проекта

Создать самостоятельную переносимую библиотеку для микроконтроллерных проектов, которая сохраняет произвольную пользовательскую структуру данных в EEPROM по кольцевому принципу и распределяет износ не только между областями записей, но и между физическими ячейками, соответствующими отдельным байтам структуры.

Пользователь библиотеки должен работать со своей обычной структурой и не заниматься расчётом адресов EEPROM, поиском места, поиском самой свежей записи, подсчётом последовательности, CRC, маркерами завершения, распределением износа и особенностями страниц конкретной EEPROM.

Основной принцип: **подключить библиотеку, настроить память один раз, затем передавать ей структуру на запись и получать структуру при чтении.**


## 2. Целевые устройства

Первая версия поддерживает строго три варианта EEPROM:

1. Внутренняя EEPROM микроконтроллеров AVR, в частности ATmega328P.
2. Внешняя последовательная EEPROM AT24C32 — 4096 байт.
3. Внешняя последовательная EEPROM AT24C64 — 8192 байт.

Другие семейства памяти в первую версию не включаются.

### 2.1. Самостоятельное подключение драйверов

Пользователь подключает только публичный заголовок:

~~~cpp
#include <Ring_EEPROM.h>
~~~

Внутри Ring_EEPROM библиотека сама подключает необходимые штатные средства платформы и выбирает внутренний драйвер в зависимости от аргумента `init()`.

Пользователь не должен отдельно подключать `EEPROM.h`, `Wire.h` или сторонние библиотеки для AT24C32/AT24C64. Ядро и драйверы остаются внутренней реализацией библиотеки.

Выбор устройства выполняется при инициализации: `INTERNAL`, `AT24C32` или `AT24C64`.

### 2.2. Определение ёмкости

Ёмкость определяется при `init()`:

- Для `INTERNAL` драйвер AVR получает размер внутренней EEPROM средствами платформы/заголовков AVR. Для AVR, предоставляющих макрос `E2END`, размер вычисляется как `E2END + 1`. Для ATmega328P это 1024 байта.
- Для `AT24C32` библиотека использует встроенную константу ёмкости 4096 байт.
- Для `AT24C64` библиотека использует встроенную константу ёмкости 8192 байт.

Размеры AT24C32 и AT24C64 задаются в дефайнах/константах внутри библиотеки. Пользователю не требуется сообщать ёмкость вручную.

AT24C32 и AT24C64 не обязаны предоставлять универсальную команду идентификации модели. Поэтому модель памяти определяется выбором пользователя в `init()`; ответ по I²C подтверждает доступность устройства, но сам по себе не доказывает, что выбрана правильная модель. Библиотека не должна обещать автоматическое различение AT24C32 и AT24C64 по одному только ответу I²C.

### 2.3. Настройки I²C

В начале публичного заголовка предусматриваются настройки по умолчанию, в том числе:

- адрес устройства I²C по умолчанию — `0x50`;
- SDA и SCL по умолчанию — штатные выводы выбранной платформы (для ATmega328P — A4 и A5).

Пользователь при необходимости меняет настройки через дефайны в начале `Ring_EEPROM.h`. В обычном случае менять их не требуется.

Пользовательский скетч не должен самостоятельно запускать I²C или подключать библиотеку Wire. Выбор и запуск нужного способа связи выполняет Ring_EEPROM.

Для ATmega328P аппаратный I²C привязан к A4/A5. Использование других выводов потребует предусмотренного внутри библиотеки программного I²C либо другого подходящего механизма платформы. Конкретный способ реализации альтернативных выводов ещё предстоит утвердить.

### 2.4. Границы рабочей области

В `init()` можно передать оба адреса рабочей области:

- `startAddress` — начальный адрес;
- `endAddress` — конечный адрес, включительно.

Если оба адреса не переданы, используется вся доступная EEPROM. Если переданы, библиотека работает только в заданных границах.

При `init()` проверяется:
- корректность типа памяти;
- доступность внешней микросхемы по I²C;
- что оба адреса находятся в физическом диапазоне выбранной EEPROM;
- что начальный адрес меньше конечного;
- что параметры области не вызывают переполнения при вычислениях.

Если границы заданы неверно, `init()` возвращает соответствующий уникальный код ошибки. Проверка достаточности области для конкретной структуры при `init()` не выполняется: размер данных на этом этапе ещё неизвестен.


## 3. Предполагаемый пользовательский интерфейс

Публичный интерфейс должен быть простым: пользователь подключает только `Ring_EEPROM.h`, выбирает тип памяти и задаёт сигнатуру при инициализации.

Предполагаемый вид API:

~~~cpp
#include <Ring_EEPROM.h>

struct MyData {
    // Пользовательские поля
};

void setup() {
    uint8_t result;

    // Вся доступная память:
    result = Ring_EEPROM.init(AT24C64, 2222);

    // Либо заданная область, адрес конца включительный:
    // result = Ring_EEPROM.init(AT24C64, 2222, 512, 4095);
}

void loop() {
    MyData data{};

    uint8_t result = Ring_EEPROM.read(data);
    // 0 — успех, ненулевое значение — конкретная ошибка.

    // Изменение data...

    result = Ring_EEPROM.write(data);
}
~~~

Тип памяти выбирается одним из трёх значений: `INTERNAL`, `AT24C32`, `AT24C64`.

### 3.1. Сигнатура

Сигнатуру задаёт пользователь. Это произвольная последовательность байтов произвольной длины, а не обязательно однобайтовое или двухбайтовое число.

Библиотека определяет длину и представление переданного значения при `init()`. Допустимые формы передачи (число, строка, массив байтов и правила определения их точной длины) должны быть реализованы так, чтобы размер не был искусственно ограничен фиксированным типом.

Сигнатура:
- записывается в начале каждой записи;
- не хранится отдельно в заголовке всего кольца;
- служит идентификатором набора/формата данных;
- при изменении сигнатуры позволяет не принимать старые записи с прежней подписью.

Сигнатура не заменяет CRC и не является криптографической защитой.

### 3.2. Единая карта кодов результата

В начале файла `Ring_EEPROM.h` должна располагаться одна общая, чёткая и жёсткая карта кодов ошибок для всей библиотеки.

Правила:
- код `0` всегда означает успешное выполнение (`RING_OK`);
- каждый ненулевой код обозначает ровно одну конкретную причину;
- все ненулевые коды уникальны глобально — независимо от того, возникла ошибка в `init()`, `read()` или `write()`;
- один и тот же код нельзя использовать для разных причин или разных операций;
- одна и та же причина не должна получать несколько синонимичных кодов;
- опубликованные номера кодов постоянны и не переиспользуются под другие причины;
- в карте должны быть отдельные однозначные причины для ошибок выбора/доступности устройства, I²C, адресов, недостатка места, физического чтения/записи, сигнатуры, CRC и повреждения записи.

Для нехватки места используется один код `ERR_NO_SPACE`: он означает, что переданные данные вместе со всеми обязательными полями записи не помещаются в выделенную область. Отдельный дублирующий код `ERR_DATA_TOO_LARGE` не вводится.

Для случая, когда при `read()` сигнатура обнаружена, но все записи-кандидаты в пределах настроенной глубины имеют неверную CRC, используется точный код `ERR_READ_CRC_FAILED`. Он является уникальным кодом единой общей карты и не переиспользуется для других причин.

Для случая, когда `read()` просмотрел выделенную область и не обнаружил ни одной записи с заданной сигнатурой, используется отдельный уникальный код `ERR_READ_NO_RECORD`. Он не совпадает с `ERR_READ_CRC_FAILED`: первый означает отсутствие записи с нужной подписью, второй — обнаруженные записи с неверной CRC.

Если `write()` физически записал запись, но последующее чтение обратно и проверка CRC выявили несовпадение, возвращается отдельный уникальный код `ERR_WRITE_VERIFY`. Ошибка физического чтения во время проверки возвращается своим кодом ошибки чтения устройства.

Все публичные операции возвращают непосредственно код результата типа `uint8_t`:
- `init(...)`;
- `read(data)`;
- `write(data)`.

Никаких отдельных методов `error()`, `lastError()` и дополнительных способов получения причины ошибки не требуется. Пользователь получает код непосредственно из вызова и сам решает, как его обрабатывать.

Пример проверки:

~~~cpp
uint8_t result = Ring_EEPROM.init(AT24C64, 2222);
if (result != 0) {
    // result уже содержит конкретный код ошибки.
}
~~~

### 3.3. Размер пользовательских данных

Размер данных определяется по объекту, переданному в `read(data)` или `write(data)` (для обычной структуры — через `sizeof(data)`). Пользователь не передаёт размер структуры отдельно в `init()`.

### 3.4. Принципы API

- Пользователь подключает только `Ring_EEPROM.h`.
- Библиотека сама выбирает внутренний драйвер по типу памяти из `init()`.
- Не требуется динамическое выделение памяти.
- Библиотека не загружает всю EEPROM в SRAM.
- Пользователь не рассчитывает физические адреса отдельных записей.
- Основные публичные операции первой версии — `init()`, `read()`, `write()`.
- Поддержка нескольких независимых экземпляров/областей остаётся отдельным вопросом проектирования; приведённый интерфейс показывает согласованный вариант единого объекта `Ring_EEPROM`.


## 4. Произвольная структура и размер данных

Библиотека не знает смысл пользовательских полей. Для неё структура — непрозрачная последовательность байтов.

Размер определяется по объекту, переданному в `read(data)` или `write(data)`. Пользователь не обязан сообщать размер в `init()`.

Для любой структуры применяется один общий механизм, независимо от того, занимает она малую часть EEPROM, больше половины памяти или почти всю выделенную область. Отдельные режимы для «маленьких», «больших» и «почти полных» структур не вводятся.

Полная запись состоит только из четырёх частей и именно в таком порядке:

~~~text
[СИГНАТУРА][НОМЕР ЗАПИСИ][ДАННЫЕ][CRC]
~~~

- Сигнатура — произвольная последовательность байтов, заданная пользователем при `init()`; её длина известна библиотеке.
- Номер записи — размер поля автоматически рассчитывает библиотека с учётом выделенной области и размера данных.
- Данные — байтовое представление пользовательской структуры.
- CRC — контрольная сумма; алгоритм и точный состав защищаемых байтов ещё предстоит утвердить.

Никаких дополнительных байтов начала/окончания, commit-маркеров, терминаторов или отдельных заголовков кольца не добавляется.

Обязательное правило размещения: полная запись со всеми сигнатурами, номером записи, пользовательскими данными и CRC должна помещаться в выделенную пользователем область вместе с теми требованиями к перемещению/журналированию, которые будут окончательно утверждены для единого алгоритма.

Остаток памяти не требует резервировать под вторую полную копию структуры. Свободные байты участвуют в общем перемещении записи по памяти. Например, если после размещения записи остаётся 10 байт, алгоритм должен учитывать и использовать эти 10 байт, а не отвергать структуру только потому, что она больше половины EEPROM.

Библиотека не обещает откат к предыдущей полной версии, если при обновлении новая запись физически перезаписывает её область. Сохранение старой версии при отключении питания не является обязательным требованием, если под неё не выделено отдельное место. Это не повод вводить специальные режимы для больших структур.

Если необходимые данные и обязательные служебные поля не помещаются в указанной области, операция возвращает единый код `ERR_NO_SPACE`.


## 5. Главная особенность: перемешивание физических адресов каждого байта

Это одна из центральных идей проекта.

### 5.1. Проблема обычной кольцевой записи

Если структура каждый раз записывается в одни и те же смещения внутри очередного слота, конкретное поле структуры может постоянно попадать в один и тот же относительный адрес. Это нежелательно, если поле годами не меняется: одна и та же физическая ячейка может получать непропорционально большую нагрузку.

Перемешивание должно затрагивать каждый байт пользовательской структуры, включая неизменяемые поля.

### 5.2. Шаг, взаимно простой с размером области

Обозначения:
- `N` — размер выделенной пользователем области кольца;
- `L` — полный размер записи: сигнатура + номер записи + пользовательские данные + CRC;
- `q` — автоматически вычисляемая корректировка шага (виртуальный промежуток);
- `P = L + q` — шаг между адресами начала последовательных записей;
- `k` — порядковый номер записи;
- `j` — смещение байта внутри полной записи.

Формат записи остаётся строго неизменным:

~~~text
[СИГНАТУРА][НОМЕР ЗАПИСИ][ДАННЫЕ][CRC]
~~~

Если полный размер записи `L` не взаимно прост с размером кольца `N`, библиотека автоматически подбирает минимальную необходимую корректировку `q`, чтобы выполнялось:

~~~text
gcd(P, N) = 1
P = L + q
~~~

Физический адрес байта полной записи определяется по модели:

~~~text
address(k, j) = (base + k * P + j) mod N
~~~

При `gcd(P, N) = 1` адрес начала записи проходит все N смещений. Поэтому для каждого фиксированного смещения `j` любой байт полной записи — в том числе сигнатура, номер, данные и CRC — со временем проходит по всем физическим адресам кольца.

**Критически важно: корректировка `q` не является частью записи.** Она существует только в расчёте адреса начала следующей записи. Библиотека не добавляет поле, байты-заполнители, терминатор или иной физически записываемый промежуток. Формат записи и её размер `L` не меняются.

Пример: если `N = 4096` и `L = 37`, то шаг 37 уже взаимно прост с 4096, поэтому `q = 0`. Если `L = 38`, библиотека может выбрать `q = 1`, получив шаг 39, взаимно простой с 4096.

Это согласованное правило вычисления шага. Окончательная схема размещения должна дополнительно учитывать циклическое пересечение границы области, перекрытие последовательных записей и поиск действительных записей; эти детали ещё подлежат проектированию и проверке.

### 5.3. Вся выделенная область участвует в кольце и циклическая адресация

`N` — это вся выделенная пользователем область EEPROM:

~~~text
N = endAddress - startAddress + 1
~~~

Внутри этой области нет отдельных служебных областей, постоянных адресов или неподвижных полей. Нельзя резервировать участок, в котором всегда хранятся сигнатура, номер записи, CRC, указатели или другие данные библиотеки.

Полная запись перемещается целиком. Сигнатура, номер записи, пользовательские данные и CRC не закреплены за физическими адресами: они перемещаются по кольцу вместе с записью.

**Циклический переход адресации должен выполняться автоматически при любой операции чтения и записи.** Достижение `endAddress` не завершает операцию и не считается ошибкой: следующий физический адрес — `startAddress`. Это правило одинаково действует для сигнатуры, номера записи, каждого байта данных и CRC.

Общее правило преобразования логического смещения в физический адрес:

~~~text
physicalAddress = startAddress + (logicalOffset mod N)
~~~

Чтение и запись полной записи должны проходить через границу кольца прозрачно для вызывающего кода. Пользователь не должен знать, пересекла ли запись конец выделенной области.

Каждый физический адрес выделенной области участвует в общем цикле перемещения. Цель — распределять запись по всей доступной пользователю области, а не только по части памяти после вычета постоянных служебных зон.

Корректировка шага `q` остаётся виртуальной и не создаёт физически зарезервированных байтов.

### 5.3.1. Проверка CRC и поиск предыдущей действительной записи

При чтении библиотека сначала определяет кандидата с самым новым номером записи и читает всю запись, автоматически переходя через границу кольца при необходимости.

После чтения данных библиотека считывает CRC, также с циклическим переходом адресации, и проверяет её.

Если CRC не совпала, библиотека не должна сразу завершать `read()` ошибкой. Она должна перейти к предыдущей записи и повторить чтение и проверку CRC. Если предыдущая запись тоже повреждена, проверяется следующая более старая запись.

Глубина поиска предыдущих записей задаётся дефайном в начале `Ring_EEPROM.h`:

~~~cpp
#ifndef RING_EEPROM_FALLBACK_DEPTH
#define RING_EEPROM_FALLBACK_DEPTH 3
#endif
~~~

Значение по умолчанию — 3. Оно означает до трёх предыдущих записей дополнительно к самой новой проверяемой записи (всего до четырёх кандидатов). Пользователь может переопределить дефайн до подключения заголовка библиотеки.

Как только найдена более старая запись с совпадающей сигнатурой и правильной CRC, `read()` возвращает её данные и код успешного выполнения. Если в пределах заданной глубины действительная предыдущая запись не найдена, `read()` возвращает строго `ERR_READ_CRC_FAILED`, если сигнатура обнаружена, но все проверенные кандидаты в пределах глубины поиска не прошли CRC. Если после просмотра выделенной области вообще не обнаружено ни одной записи с заданной сигнатурой (пустая память, другая сигнатура или другая программа), `read()` возвращает строго `ERR_READ_NO_RECORD`.

Точный способ перечисления предыдущих кандидатов и учёт пропусков/прерванных попыток записи должны быть согласованы при проектировании алгоритма номера записи и физического размещения. Само требование отката на более старую запись и глубина поиска уже согласованы.
### 5.4. Дополнительных байтов в структуре нет

Перемешивание не меняет пользовательскую структуру и не требует добавлять в неё фиктивные поля. Все адреса, смещения и служебные данные — внутренняя ответственность библиотеки.

### 5.5. Автоматический размер номера записи

Размер поля номера записи библиотека выбирает автоматически. Пользователь не задаёт тип счётчика и не выбирает его разрядность.

Обозначения:
- `N` — размер выделенной рабочей области;
- `S` — длина сигнатуры;
- `D` — размер пользовательских данных, известный при `read()` или `write()`;
- `C` — размер CRC;
- `K` — максимальное количество различных записей, которые могут одновременно присутствовать/участвовать в определении порядка при окончательной схеме размещения;
- `B` — выбираемое количество байтов номера записи.

Для счётчика из B байтов количество различных значений равно `M = 256^B`, а максимальное числовое значение — `M - 1`.

Согласованное правило: библиотека выбирает минимальное B, при котором диапазон счётчика больше удвоенного K (`M > 2K`). Это даёт запас для однозначного сравнения номеров при циклическом переполнении, при условии что окончательный алгоритм соблюдает принятую границу числа одновременно учитываемых записей.

Полный размер одной записи:

~~~text
L = S + B + D + C
~~~

При одинаковых размерах памяти/области, сигнатуры и пользовательских данных библиотека всегда должна вычислять одинаковый B и одинаковый максимальный номер. Правило выбора B не должно зависеть от истории перезапусков или предыдущих записей.

Точное вычисление K зависит от ещё не утверждённой схемы размещения, поэтому формула выбора B согласована как принцип, но окончательная реализация будет завершена после определения физической модели кольца.


## 6. Кольцевая запись и поиск самой свежей записи

Библиотека должна:
- самостоятельно выбирать физическое расположение очередной записи;
- записывать поля в порядке `сигнатура → номер записи → данные → CRC`;
- находить самую свежую действительную запись после перезапуска питания;
- определять порядок записей по номеру с учётом циклического переполнения;
- не полагаться на RAM для восстановления состояния;
- при поиске проверять сигнатуру и CRC;
- если CRC самой новой записи неверна, последовательно проверять предыдущие записи до установленной глубины поиска;
- вернуть данные первой найденной более старой записи с совпадающей сигнатурой и правильной CRC;
- если в пределах глубины поиска действительной записи нет, вернуть соответствующий уникальный код результата.

Никаких дополнительных байтов завершения или commit-маркеров в формат записи не вводится.

Физическая схема размещения, правило поиска по всей области и разрешение неоднозначностей ещё требуют проектирования и проверки.


## 7. Целостность данных и CRC

CRC — обязательное последнее поле каждой записи:

~~~text
[СИГНАТУРА][НОМЕР ЗАПИСИ][ДАННЫЕ][CRC]
~~~

### 7.1. Единый потоковый механизм с автоматически выбираемой шириной

Утверждён вариант с одним общим потоковым механизмом CRC. Библиотека не использует одну неизменную ширину для всех записей: размер поля CRC автоматически выбирается по длине защищаемой последовательности.

Длина защищаемой последовательности:

~~~text
M = S + B + D
~~~

где:
- `S` — длина сигнатуры;
- `B` — размер номера записи;
- `D` — размер пользовательских данных.

CRC рассчитывается по сигнатуре, номеру записи и данным. Само поле CRC в расчёт не входит.

Предусматриваются ширины CRC-8, CRC-16 и CRC-32: соответственно 1, 2 и 4 байта в записи. Для выбранной ширины библиотека применяет соответствующий полином и параметры CRC, подобранные с учётом длины защищаемой последовательности.

Это один потоковый интерфейс вычисления: инициализация состояния CRC, последовательная подача очередного байта, получение итогового значения. При чтении и записи не требуется собирать всю запись или структуру во временный массив.

**Точные пороги выбора CRC-8/CRC-16/CRC-32, конкретные полиномы и остальные параметры каждого варианта ещё предстоит выбрать и проверить.** Их нужно выбирать по длине сообщения и требуемым свойствам обнаружения ошибок, а не произвольно.

### 7.2. Потоковая запись

При `write(data)` библиотека последовательно записывает:
1. сигнатуру;
2. номер записи;
3. байты пользовательских данных.

По мере прохождения каждого байта библиотека обновляет потоковое состояние CRC. После последнего байта данных она записывает вычисленную CRC в конец записи.

Полная структура пользователя не копируется во временный буфер.

### 7.3. Обязательная проверка записи после физической записи

После записи всей записи библиотека обязана прочитать её обратно из EEPROM и проверить результат.

Проверка выполняется потоком:
1. повторно читаются сигнатура, номер записи и все байты данных;
2. по каждому прочитанному байту заново вычисляется CRC;
3. читается сохранённое в EEPROM поле CRC;
4. вычисленное значение сравнивается с прочитанным значением CRC.

Циклическая адресация действует и во время этой проверки: переход через `endAddress` на `startAddress` выполняется автоматически.

Если физическое чтение при проверке невозможно, возвращается соответствующий код ошибки чтения устройства. Если запись прочитана, но вычисленная CRC не совпала с CRC, сохранённой в EEPROM, `write()` возвращает отдельный уникальный код `ERR_WRITE_VERIFY` из единой глобальной карты ошибок. Только после успешной проверки `write()` возвращает `0`.

Проверка не требует буфера размером с пользовательскую структуру: используются состояние CRC и небольшой рабочий буфер драйвера.

### 7.4. Потоковое чтение без предварительной загрузки структуры

При `read(data)` сначала проверяется кандидат без записи пользовательских данных в структуру:
1. читаются сигнатура и номер записи;
2. все байты данных последовательно читаются из EEPROM и сразу подаются в вычислитель CRC;
3. читается сохранённое поле CRC;
4. вычисленная CRC сравнивается с сохранённой.

Только если CRC совпала, библиотека выполняет второй проход: повторно читает байты пользовательских данных и записывает их непосредственно в объект, переданный в `read(data)`.

Если CRC не совпала, структура пользователя не заполняется данными из этого кандидата; библиотека пробует предыдущую запись в пределах `RING_EEPROM_FALLBACK_DEPTH`.

Такой двухпроходный подход позволяет сначала проверить целостность записи, а затем загрузить данные, не выделяя массив размером со структуру.

### 7.5. Отсутствие дополнительных маркеров

Дополнительные маркеры завершения/commit, байты окончания и отдельные служебные поля в формат не добавляются. CRC остаётся последним и единственным контрольным полем записи.

## 8. Отключение питания и поведение при прерывании записи

Библиотека использует единый механизм размещения для структур любого размера. Обязательного хранения двух полных независимых копий нет.

Если свободное место позволяет переместить новую запись, не затронув предыдущую, алгоритм может сохранить предыдущую запись до завершения новой. Но это не является универсальной гарантией.

Если новая запись при перемещении перезаписывает физическую область предыдущей, отключение питания может повредить предыдущие данные. Библиотека не обязана обеспечивать откат к старой полной версии в такой ситуации.

После включения питания библиотека должна искать записи по сигнатуре и номеру, сначала проверять самую новую запись по CRC, а при несовпадении CRC переходить к более старым записям в пределах `RING_EEPROM_FALLBACK_DEPTH`. Если находится предыдущая запись с правильной CRC, она возвращается пользователю. Циклическая адресация при этом действует на всех этапах чтения, включая переход через конец выделенной области. Точное поведение при прерывании на каждом этапе зависит от окончательной схемы размещения и последовательности записи.

Открытый вопрос — какие именно гарантии можно честно обеспечить без commit-маркера и без обязательной второй копии. Нельзя заявлять атомарность или сохранность старой версии, пока это не доказано моделированием и испытаниями.

## 9. Ограничения физической памяти

### 9.1. Внутренняя EEPROM микроконтроллера

Драйвер должен учитывать:
- доступную ёмкость;
- допустимый размер адреса;
- особенности побайтового чтения/записи;
- особенности API конкретной платформы;
- ресурс циклов записи, заявленный производителем.

### 9.2. AT24C32 и AT24C64

Драйвер должен учитывать:
- ёмкость 4096/8192 байт соответственно;
- адресацию памяти;
- размер страницы записи конкретной модели;
- запрет пересечения границы страницы одной операцией Page Write;
- время внутреннего цикла записи и подтверждение готовности;
- адрес устройства на I²C и аппаратные адресные выводы.

Ядро должно иметь возможность передавать драйверу диапазоны данных, не предполагая, что любой диапазон можно записать одной физической операцией.

## 10. Ресурсы микроконтроллера

Приоритет — пригодность для небольших AVR, в том числе ATmega328P с ограниченной SRAM.

Предварительные требования:
- без malloc, new и динамического выделения памяти в рабочем алгоритме;
- не загружать весь EEPROM в оперативную память;
- использовать небольшой фиксированный буфер;
- не создавать большие временные массивы;
- по возможности поддерживать потоковое чтение/запись блоками;
- контролировать размер кода и потребление SRAM;
- не требовать RTOS.

Нужно определить допустимый размер внутреннего буфера и можно ли сделать его настраиваемым при компиляции.

## 11. Несколько независимых областей и экземпляров

Желательно поддержать несколько объектов библиотеки:
- разные области одной EEPROM;
- разные физические EEPROM;
- разные типы структур.

Каждый экземпляр должен иметь собственные настройки и состояние. Данные разных экземпляров не должны пересекаться, если пользователь выделил непересекающиеся области.

Нужно решить, как библиотека будет проверять границы областей и обнаруживать некорректную конфигурацию.


## 12. Инициализация и первое использование

Публичная операция называется `init()`.

При инициализации библиотека:
1. принимает тип памяти: `INTERNAL`, `AT24C32` или `AT24C64`;
2. принимает пользовательскую сигнатуру и определяет её длину/представление;
3. определяет физическую ёмкость выбранной EEPROM;
4. для внешней EEPROM проверяет доступность устройства по настроенному адресу I²C;
5. принимает либо всю память, либо явно заданные начальный и конечный адреса (конечный адрес включительный);
6. проверяет границы относительно физической ёмкости и корректность диапазона;
7. сохраняет настройки, необходимые последующим `read()` и `write()`.

`init()` не получает и не проверяет размер пользовательской структуры. Размер данных ещё неизвестен и определяется позже при `read(data)` или `write(data)`.

Если адреса области не переданы, используется вся доступная память.

При успешной инициализации возвращается `0`; при ошибке возвращается конкретный ненулевой код из единой карты ошибок.

`init()` не должна автоматически стирать или форматировать EEPROM.

## 13. Совместимость структур и версий

На первом этапе можно рассматривать структуру как непрозрачный блок байтов фиксированного размера. Но это означает, что изменение состава/порядка полей или компиляторного выравнивания структуры может сделать ранее записанные данные несовместимыми с новой прошивкой.

Нужно решить:
- требуется ли хранить идентификатор формата/версию структуры;
- должна ли библиотека проверять ожидаемый размер;
- нужна ли поддержка пользовательского преобразования старого формата в новый;
- будет ли библиотека отвечать только за байтовое сохранение, оставляя миграцию приложению.


## 14. Публичные операции первой версии

Согласованный основной набор:

| Операция | Назначение | Результат |
|---|---|---|
| `init(type, signature[, startAddress, endAddress])` | Выбрать память, определить сигнатуру и настроить рабочую область | `uint8_t`: 0 — успех, иначе уникальный код ошибки |
| `write(data)` | Сохранить новую запись, затем прочитать её обратно и проверить CRC | `uint8_t`: 0 — запись и проверка успешны, иначе уникальный код ошибки |
| `read(data)` | Найти и восстановить самую свежую действительную запись подходящего размера | `uint8_t`: 0 — успех, иначе уникальный код ошибки |

Все три операции используют одну глобальную карту кодов результата. Отдельный метод получения последней ошибки не нужен.

Дополнительные публичные операции (`hasData()`, `clear()`, `format()` и т.п.) пока не входят в согласованный обязательный интерфейс.

## 18. Текущий статус

### Согласовано

- Отдельная самостоятельная библиотека `Fmulder007/Ring_EEPROM`.
- Первая версия поддерживает только внутреннюю AVR EEPROM, AT24C32 и AT24C64.
- Пользователь подключает только `Ring_EEPROM.h`; необходимые штатные заголовки и драйверы подключаются внутри библиотеки.
- Тип памяти выбирается при `Ring_EEPROM.init(INTERNAL|AT24C32|AT24C64, signature, ...)`.
- Ёмкость AT24C32 — 4096 байт, AT24C64 — 8192 байт; для внутренней AVR EEPROM размер определяется средствами платформы (для поддерживающих `E2END` — `E2END + 1`).
- Адрес I²C по умолчанию — `0x50`; SDA/SCL и адрес настраиваются дефайнами внутри публичного заголовка.
- Если границы не заданы, используется вся EEPROM; иначе задаются начальный и конечный адреса, причём конечный адрес включительный.
- `init()` проверяет устройство, доступность внешней EEPROM и физические границы, но не размер пользовательской структуры.
- Сигнатуру задаёт пользователь; её длина определяется при `init()`; каждая запись начинается с полной сигнатуры.
- Само кольцо отдельно не помечается; сигнатура не хранится отдельно.
- Формат записи строго такой: `[СИГНАТУРА][НОМЕР ЗАПИСИ][ДАННЫЕ][CRC]`.
- Дополнительные байты завершения, терминаторы и commit-маркеры не вводятся.
- Размер пользовательских данных определяется объектом, переданным в `read()` или `write()`.
- Для любой структуры действует единый алгоритм; не вводятся отдельные режимы по размеру и не требуется вторая полная копия.
- Полная запись перемещается как единое целое; её формат остаётся `[СИГНАТУРА][НОМЕР ЗАПИСИ][ДАННЫЕ][CRC]`.
- Шаг между началами записей равен `P = L + q`, где `L` — полный размер записи, а `q` — автоматически подобранная виртуальная корректировка, обеспечивающая `gcd(P, N) = 1`.
- `q` существует только в расчёте адресации: не записывается в EEPROM, не добавляет байтов и не меняет формат записи.
- `N` — вся выделенная пользователем область от начального до конечного адреса включительно; внутри кольца нет неподвижных или зарезервированных служебных областей, все поля полной записи перемещаются по всей области.
- Адресация чтения и записи циклическая: после `endAddress` следующий адрес автоматически `startAddress`; это относится ко всем полям записи и CRC.
- При несовпадении CRC самой новой записи библиотека пытается прочитать предыдущие записи. Дефайн `RING_EEPROM_FALLBACK_DEPTH` по умолчанию равен 3 и задаёт число предыдущих кандидатов сверх самой новой записи; при успехе возвращаются данные первой более старой записи с верной CRC.
- Если сигнатуры найдены, но все проверенные кандидаты в пределах глубины поиска не прошли CRC, `read()` возвращает код `ERR_READ_CRC_FAILED` из единой глобальной карты ошибок.
- CRC использует один потоковый механизм; ширина автоматически выбирается по длине защищаемой последовательности `S + B + D` (CRC-8, CRC-16 или CRC-32). Точные пороги, полиномы и параметры ещё предстоит утвердить.
- CRC рассчитывается последовательно по сигнатуре, номеру записи и пользовательским данным; временный массив всей структуры не создаётся.
- `read()` сначала потоково проверяет всю запись по CRC, не заполняя пользовательскую структуру, и только при совпадении выполняет второй проход для загрузки данных непосредственно в объект пользователя.
- `write()` после записи обязательно перечитывает запись из EEPROM, повторно вычисляет CRC и сравнивает её с сохранённой. При несовпадении возвращает уникальный код `ERR_WRITE_VERIFY`; при успехе возвращает `0`.
- Если ни одной записи с заданной сигнатурой в выделенной области не найдено, `read()` возвращает код `ERR_READ_NO_RECORD`.
- Все необходимые данные и служебные поля должны помещаться в выделенной области; если не помещаются, возвращается один код `ERR_NO_SPACE`.
- Предыдущая полная запись не обязана сохраняться при перезаписи её области; универсальный откат не обещается.
- Размер поля номера записи выбирает библиотека. Выбирается минимальное B, для которого `256^B > 2K`; максимальное значение счётчика — `256^B - 1`. Для одинаковых параметров результат должен быть одинаковым.
- Все публичные операции `init()`, `read()`, `write()` возвращают `uint8_t`: 0 — успех, ненулевое значение — конкретный код ошибки.
- В начале `Ring_EEPROM.h` будет одна глобальная карта ошибок. Все коды уникальны для всей библиотеки, независимо от операции; отдельного метода получения ошибки нет.
- Для нехватки места существует только один код `ERR_NO_SPACE`; синонимичный `ERR_DATA_TOO_LARGE` не вводится.
- Сначала обсуждение и документация, затем реализация после явного утверждения.
