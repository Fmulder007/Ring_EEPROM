# Ring_EEPROM — план проектирования универсальной библиотеки кольцевой записи

> **Статус документа:** проект обсуждения.  
> **Назначение:** собрать в одном месте согласованные идеи, предварительные решения, технические ограничения и открытые вопросы до начала реализации.  
> **Язык документации проекта:** русский.  
> **Важно:** это не окончательная спецификация алгоритма. Предварительные решения требуют обсуждения и утверждения.

---

## 1. Цель проекта

Создать самостоятельную переносимую библиотеку для микроконтроллерных проектов, которая сохраняет произвольную пользовательскую структуру данных в EEPROM по кольцевому принципу и распределяет износ не только между областями записей, но и между физическими ячейками, соответствующими отдельным байтам структуры.

Пользователь библиотеки должен работать со своей обычной структурой и не заниматься расчётом адресов EEPROM, поиском места, поиском самой свежей записи, подсчётом последовательности, CRC, маркерами завершения, распределением износа и особенностями страниц конкретной EEPROM.

Основной принцип: **подключить библиотеку, настроить память один раз, затем передавать ей структуру на запись и получать структуру при чтении.**

## 2. Целевые устройства

Первая цель — поддержка двух семейств EEPROM:

1. Внутренняя EEPROM микроконтроллеров AVR (в частности, ATmega328P).
2. Внешние последовательные EEPROM семейства 24C:
   - AT24C32 — 4096 байт;
   - AT24C64 — 8192 байт.

Архитектура не должна ограничиваться этими моделями. В будущем можно добавлять другие микроконтроллеры, EEPROM и внешние носители через новые драйверы/адаптеры.

### 2.1. Разделение алгоритма и физического устройства

Предлагается разделить библиотеку на две независимые части:

- **Ядро Ring_EEPROM** — логика кольца, размещение данных, поиск последней записи, контроль целостности и восстановление.
- **Драйвер памяти** — чтение, запись, получение ёмкости и учёт физических ограничений конкретного устройства.

Ядро не должно быть жёстко привязано к вызовам EEPROM.read() или к конкретной реализации AT24C32.

Драйвер должен сообщать ядру как минимум:
- доступную ёмкость устройства или предоставленной области;
- возможность чтения байта/диапазона;
- возможность записи байта/диапазона;
- ограничения записи (например, размер страницы и запрет перехода через границу страницы одной физической операцией);
- при необходимости — готовность устройства после записи.

### 2.2. Определение ёмкости

Желаемое поведение: библиотека сама получает размер памяти и рассчитывает размещение.

Техническое уточнение: универсальное ядро не может безошибочно определить физическую модель любой EEPROM только по факту подключения. Ёмкость должна сообщаться драйвером. Для внутренней EEPROM драйвер может получать её из возможностей платформы/компилятора; для AT24C32/64 конкретный драйвер должен знать модель или получать её из конфигурации.

Таким образом, пользователь не обязан вручную считать адреса и размеры, но конкретное устройство/драйвер должно быть однозначно определено.

## 3. Предполагаемый пользовательский интерфейс

Ниже приведён эскиз, а не утверждённый API.

~~~cpp
#include <Ring_EEPROM.h>
#include <Ring_EEPROM_AVR.h>
// либо драйвер для AT24C32/AT24C64

struct MyData {
    // Пользовательские поля
};

RingEEPROM<MyData> memory;

void setup() {
    memory.begin(EEPROM_DEVICE /* и, возможно, параметры области */);
}

void loop() {
    MyData data{};

    if (memory.read(data)) {
        // Получена последняя корректная структура.
    }

    // Изменение data...

    if (memory.write(data)) {
        // Запись выполнена.
    }
}
~~~

Желаемые свойства интерфейса:
- пользователь передаёт обычную структуру;
- размер структуры определяется автоматически через sizeof(T);
- чтение возвращает признак успеха/неуспеха;
- запись возвращает признак успеха/неуспеха;
- библиотека самостоятельно выбирает физические адреса;
- можно создавать несколько независимых объектов библиотеки для разных областей/устройств;
- не требуется динамическое выделение памяти;
- библиотека не должна требовать загрузки всей EEPROM в SRAM.

Нужно отдельно решить, будет ли пользователь задавать только устройство, или также начальный адрес и длину выделенной области. Поддержка выделенной области внутри большой EEPROM желательна, чтобы несколько подсистем могли независимо использовать разные диапазоны.

## 4. Произвольная структура и размер данных

Библиотека не должна знать смысл пользовательских полей. Для неё структура — непрозрачный набор байтов.

Она должна уметь сохранять и восстанавливать структуры разного размера, в пределах физически доступной области и с учётом служебных данных библиотеки.

Желаемое требование: структура может занимать больше половины EEPROM. Например, на AT24C32 структура размером 3000 байт не должна автоматически отвергаться только потому, что она больше 2048 байт.

Однако должны соблюдаться физические ограничения:
- полезные данные плюс обязательные служебные данные должны помещаться в выделенной области;
- структура больше доступной области не может быть сохранена без дополнительного внешнего хранения или изменения формата;
- чем ближе размер структуры к полной ёмкости, тем меньше остаётся пространства для журнала, маркеров и восстановления после прерывания.

Особенно важно отдельно спроектировать режимы работы для структур, занимающих небольшую часть памяти, больше половины памяти и почти всю доступную память.

## 5. Главная особенность: перемешивание физических адресов каждого байта

Это одна из центральных идей проекта.

### 5.1. Проблема обычной кольцевой записи

Если структура каждый раз записывается в одни и те же смещения внутри очередного слота, то конкретное поле структуры всегда попадает в один и тот же относительный адрес внутри слота.

Это может быть нежелательно, если отдельное поле годами не меняется. Например, в структуре есть байт со значением 9, который при каждой записи получает то же значение. Даже если остальные поля меняются, конкретная физическая ячейка может получать непропорционально большую нагрузку.

Нам нужна защита не только от износа между слотами, но и от локального износа отдельных байтов структуры.

### 5.2. Идея шага, взаимно простого с размером области

Обозначения:
- N — количество адресуемых байтов в области, которую алгоритм использует для перемешивания;
- P — шаг смещения физического размещения при очередной логической записи;
- k — номер очередной записи;
- j — смещение байта внутри пользовательских данных.

Предварительная математическая модель для физического адреса байта:

~~~text
address(k, j) = (base + k * P + j) mod N
~~~

Если gcd(P, N) = 1, то последовательность k * P mod N проходит через все N возможных смещений, прежде чем повториться.

Следствие: для каждого фиксированного байта структуры (j) его физический адрес со временем проходит по всей области из N байтов, а не остаётся постоянно в одном и том же месте.

### 5.3. Автоматический подбор шага

Предложение:
1. Ядро получает размер рабочей области N.
2. Выбирает исходный шаг, связанный с размером записи/полезных данных.
3. Проверяет gcd(P, N).
4. Если шаг не взаимно прост с N, увеличивает/изменяет его до получения gcd(P, N) = 1.
5. Использует выбранный шаг для перемещения физического размещения при последующих записях.

Идея пользователя об автоматическом добавлении одного байта относится именно к этому принципу: не допустить повторяющегося короткого цикла смещений из-за общего делителя. В реализации это должно быть обобщено до автоматического подбора подходящего P, а не обязательно ограничиваться ровно одним увеличением.

**Важно:** взаимная простота шага и размера области обеспечивает полный цикл стартовых смещений в указанной математической модели. Но сама по себе она ещё не решает вопросы перекрытия соседних снимков структуры, хранения метаданных и атомарности. Это отдельная часть алгоритма, которую необходимо спроектировать и проверить.

### 5.4. Что считать областью N

Открытый вопрос: N — это:
- вся выделенная пользователем область EEPROM;
- только область полезных данных после вычета служебных байтов;
- логическое адресное пространство, в котором данные размещаются с циклическим переходом через границу.

Нужно выбрать вариант так, чтобы служебные данные (счётчик, CRC, commit и указатели) сами не стали постоянными горячими точками износа.

### 5.5. Важное требование

Дополнительный байт для перемешивания не должен становиться частью пользовательской структуры. Пользователь передаёт и получает исходный тип без искусственных полей и без необходимости менять его объявление. Любые байты выравнивания/служебные данные — внутренняя ответственность библиотеки.

## 6. Кольцевая запись и поиск самой свежей записи

Библиотека должна:
- самостоятельно выбирать место для очередной записи;
- вести номер/поколение записи или другой надёжный признак порядка;
- находить самую свежую действительную запись после перезапуска питания;
- не полагаться на RAM для восстановления состояния;
- корректно обрабатывать переполнение счётчика последовательности;
- пропускать повреждённые или незавершённые записи;
- возвращать false, если действительной записи нет.

Нужно определить, будет ли библиотека хранить несколько независимых полных снимков структуры или использовать иной формат размещения/журналирования.

## 7. Целостность данных и завершение записи

В качестве предварительной идеи обсуждались:
- CRC для проверки целостности;
- служебный маркер завершения (commit marker);
- запись маркера последним, после полезных данных и остальных метаданных;
- признание записи действительной только при корректной CRC и корректном маркере.

Это помогает отличать завершённую запись от прерванной, но окончательная схема ещё не утверждена.

Открытые вопросы:
- CRC-8, CRC-16 или другой алгоритм?
- Должен ли алгоритм CRC быть настраиваемым?
- Как хранить и перемещать CRC вместе с записью?
- Как гарантировать, что сам маркер commit не станет горячей ячейкой?
- Как избежать ложного признания старой/частично перезаписанной записи действительной?
- Какова точная последовательность физических операций для каждого типа EEPROM?

## 8. Отключение питания и атомарность

Нужно определить гарантию поведения при отключении питания в любой момент записи.

Желаемое поведение для обычного режима:
- последняя завершённая запись остаётся доступной;
- незавершённая новая запись не должна ошибочно считаться действительной;
- после включения питания библиотека самостоятельно находит последнюю действительную версию.

Но есть фундаментальное ограничение.

Если пользовательская структура занимает больше половины области, две полные независимые копии (старая и новая) вместе со служебными данными могут не поместиться. Если новая структура записывается поверх старой, отключение питания может повредить старую версию до того, как новая будет полностью записана.

Поэтому нельзя обещать безусловное сохранение предыдущей полной версии при любой ёмкости структуры без дополнительного пространства или более сложного протокола. Нужно определить:
- гарантированный режим с сохранением предыдущей версии, когда хватает места;
- возможный режим с ограниченной гарантией для очень больших структур;
- либо иной алгоритм, который позволит усилить гарантию без второй полной копии.

Это один из главных архитектурных вопросов проекта.

## 9. Ограничения физической памяти

### 9.1. Внутренняя EEPROM микроконтроллера

Драйвер должен учитывать:
- доступную ёмкость;
- допустимый размер адреса;
- особенности побайтового чтения/записи;
- особенности API конкретной платформы;
- ресурс циклов записи, заявленный производителем.

### 9.2. AT24C32 и AT24C64

Драйвер должен учитывать:
- ёмкость 4096/8192 байт соответственно;
- адресацию памяти;
- размер страницы записи конкретной модели;
- запрет пересечения границы страницы одной операцией Page Write;
- время внутреннего цикла записи и подтверждение готовности;
- адрес устройства на I²C и аппаратные адресные выводы.

Ядро должно иметь возможность передавать драйверу диапазоны данных, не предполагая, что любой диапазон можно записать одной физической операцией.

## 10. Ресурсы микроконтроллера

Приоритет — пригодность для небольших AVR, в том числе ATmega328P с ограниченной SRAM.

Предварительные требования:
- без malloc, new и динамического выделения памяти в рабочем алгоритме;
- не загружать весь EEPROM в оперативную память;
- использовать небольшой фиксированный буфер;
- не создавать большие временные массивы;
- по возможности поддерживать потоковое чтение/запись блоками;
- контролировать размер кода и потребление SRAM;
- не требовать RTOS.

Нужно определить допустимый размер внутреннего буфера и можно ли сделать его настраиваемым при компиляции.

## 11. Несколько независимых областей и экземпляров

Желательно поддержать несколько объектов библиотеки:
- разные области одной EEPROM;
- разные физические EEPROM;
- разные типы структур.

Каждый экземпляр должен иметь собственные настройки и состояние. Данные разных экземпляров не должны пересекаться, если пользователь выделил непересекающиеся области.

Нужно решить, как библиотека будет проверять границы областей и обнаруживать некорректную конфигурацию.

## 12. Инициализация и первое использование

Желаемая модель:
- begin() проверяет конфигурацию;
- получает возможности драйвера и размер доступной области;
- рассчитывает внутреннюю раскладку;
- определяет, есть ли уже действительные данные;
- не стирает и не форматирует EEPROM автоматически без необходимости.

Открытые вопросы:
- нужен ли отдельный format()/reset()?
- как распознать пустую или ранее неинициализированную область?
- как отличить область другой версии формата?
- как библиотека должна вести себя при изменении размера пользовательской структуры между версиями прошивки?

## 13. Совместимость структур и версий

На первом этапе можно рассматривать структуру как непрозрачный блок байтов фиксированного размера. Но это означает, что изменение состава/порядка полей или компиляторного выравнивания структуры может сделать ранее записанные данные несовместимыми с новой прошивкой.

Нужно решить:
- требуется ли хранить идентификатор формата/версию структуры;
- должна ли библиотека проверять ожидаемый размер;
- нужна ли поддержка пользовательского преобразования старого формата в новый;
- будет ли библиотека отвечать только за байтовое сохранение, оставляя миграцию приложению.

## 14. Предварительный список публичных операций

Кандидаты, не окончательный API:

| Операция | Назначение |
|---|---|
| begin(...) | Настроить экземпляр и проверить область |
| write(data) | Сохранить новую версию структуры |
| read(data) | Найти и вернуть самую свежую действительную версию |
| hasData() | Проверить наличие действительной записи |
| clear() | Логически сбросить область, если такая операция будет нужна |
| format() | Инициализировать область с явным разрешением на стирание |

Нужно решить, какие операции действительно необходимы. API должен оставаться небольшим и понятным.

## 15. Вопросы для утверждения архитектуры

Ниже собраны вопросы, которые необходимо последовательно обсудить. До их решения нельзя считать алгоритм окончательно утверждённым.

### A. Подключение и конфигурация
1. Пользователь указывает только объект/драйвер EEPROM, или также начальный адрес и размер области?
2. Для AT24C32/64 модель задаётся выбором драйвера, шаблонным параметром или конфигурацией?
3. Нужна ли возможность использовать несколько независимых областей одной EEPROM?

### B. Перемешивание адресов
4. Подтверждаем ли принцип: для фиксированного байта структуры его физический адрес должен проходить по всей рабочей области?
5. Считать ли N размером всей выделенной области или только области данных?
6. Выбирать ли P автоматически начиная с размера полезной записи/её физического формата и изменяя до gcd(P, N) = 1?
7. Как разместить служебные метаданные так, чтобы они также не стали горячими точками?
8. Должно ли перемешивание охватывать все байты пользовательской структуры, включая неизменяемые поля, без исключений?

### C. Большие структуры
9. Подтверждаем ли поддержку структуры размером более половины EEPROM, если полезные данные и обязательные служебные данные помещаются?

## 18. Текущий статус

### Согласовано как цели проекта
- Самостоятельная универсальная библиотека в отдельном репозитории Fmulder007/Ring_EEPROM.
- Поддержка внутренней EEPROM МК и внешних AT24C32/AT24C64.
- Пользователь передаёт и получает обычную структуру; библиотека работает с её байтовым представлением.
- Библиотека сама выбирает место записи и находит самую свежую действительную запись.
- Кольцевой принцип и распределение износа.
- Перемешивание физических адресов должно затрагивать каждый байт структуры, в том числе неизменяемые поля.
- Для полного цикла смещений рассматривается шаг P, взаимно простой с размером рабочей области N.
- Структуры размером больше половины памяти должны поддерживаться, если хватает места на полезные и служебные данные.
- Минимальное использование SRAM и отсутствие динамического выделения памяти.
- Сначала обсуждение и документация, затем реализация после явного утверждения.

### Предварительные предложения, требующие утверждения
- Архитектура «общее ядро + драйвер конкретной EEPROM».
- CRC и маркер завершения записи.
- Автоматический подбор шага P.
- Несколько независимых экземпляров/областей.
- Фиксированный небольшой буфер.
- Проверка конфигурации при begin().

### Не решено
- Точная физическая схема размещения и перекрытия записей.
- Значение и состав рабочей области N.
- Как хранить метаданные без горячих точек износа.
- Как обеспечить атомарность при структуре больше половины памяти.
- Точные гарантии при внезапном отключении питания.
- Точный API и формат драйверов.
- CRC, формат commit и счётчик поколений.
- Поведение при изменении версии/размера структуры.
- Допустимый резерв памяти и размер SRAM-буфера.
